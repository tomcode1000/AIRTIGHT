AIRTIGHT - UI DESIGN BRIEF
For: Figma designer
Version: 1.0
================================================================================

--------------------------------------------------------------------------------
0. WHAT THIS PRODUCT IS (read this first)
--------------------------------------------------------------------------------

AIRTIGHT is a payment safety layer for autonomous AI agents that spend money.

The problem: agents now pay each other automatically. If an agent is killed
mid-payment (crash, restart, network drop), it wakes up with no idea whether
the money left its wallet. If it retries, it pays twice. If it doesn't, it is
stuck having possibly paid for nothing.

What AIRTIGHT does: it writes the signed payment instruction into persistent
memory BEFORE the money moves, never after. When the agent wakes up, it
re-submits that exact stored instruction. Because each payment carries a
one-time-use number (a "nonce") that the blockchain burns on first use, the
same instruction can never move money twice.

The one-sentence version for the UI:
    "It writes to memory before it acts, so a crash can never make it pay twice."

The proof, which appears throughout the UI:
    nonce stored in memory  ==  nonce burned on-chain

This is built for a hackathon (Sibyl Labs Memory Hackathon). The website will
be used LIVE during a recorded demo video. That constraint drives everything
below.

--------------------------------------------------------------------------------
1. WHO SEES THIS
--------------------------------------------------------------------------------

Audience 1 (primary): hackathon judges watching a 2-5 minute video, and then
clicking through the site themselves. Technical. Skeptical. They are
specifically checking whether the memory layer is doing real work or is
decoration.

Audience 2: developers who might use the layer in their own agent.

NOT a consumer product. No onboarding flows, no pricing page, no signup.

--------------------------------------------------------------------------------
2. HARD CONSTRAINTS (please do not design around these)
--------------------------------------------------------------------------------

A. VIDEO LEGIBILITY IS THE TOP PRIORITY.
   The site will be screen-recorded and watched on phones. Body text must never
   be smaller than 16px. Data/monospace values never smaller than 15px. Any
   number that matters to the story (hashes, states, verdicts) should be 18px+.
   Assume the viewer sees it for 4 seconds on a small screen.

B. DARK THEME ONLY. This is an instrument, not a brochure. No light mode
   needed. High contrast, near-black background.

C. REAL DATA, NOT PLACEHOLDER SHAPES. Every screen shows actual values -
   transaction hashes, timestamps, state names. Design with real strings at
   real lengths (a hash is 66 characters). Show how they truncate.

D. NO STOCK ILLUSTRATION, NO 3D BLOBS, NO AI-ROBOT IMAGERY. The aesthetic is
   closer to an aircraft instrument panel or a trading terminal than to a SaaS
   landing page.

E. THE UI MUST BE OPERABLE LIVE. Buttons trigger real actions during the demo
   (start a deal, kill the agent, delete the memory). Design real button states
   and real in-progress states, because they will be seen.

--------------------------------------------------------------------------------
3. TONE AND VISUAL DIRECTION
--------------------------------------------------------------------------------

Words to design toward:   instrument, forensic, black-box recorder, evidence,
                          receipt, cockpit, ledger
Words to design away from: friendly, playful, gradient, glassmorphism, crypto-bro,
                          neon cyberpunk

Reference feeling (do not copy): flight data recorder readouts, Stripe's
dashboard density without its brightness, a terminal that someone designed
properly.

TYPOGRAPHY
- One monospace family for all data, hashes, states, timestamps, logs.
  Suggested: JetBrains Mono, IBM Plex Mono, or Berkeley Mono.
- One neutral sans for prose and headings. Suggested: Inter, or the same mono
  used at heavier weight for a single-typeface design (this is acceptable and
  may look stronger).
- Numbers must be tabular/monospaced so columns align.

COLOR - semantic, not decorative. These meanings are fixed by the product:
- Background:        near-black (#0B0D0F to #101316 range)
- Surface/panel:     one step lighter, subtle border rather than shadow
- Primary text:      near-white, not pure white
- Dim text:          ~55% opacity, for labels and timestamps
- GREEN   = RESUME / verified / match / CLOSED         (safe, proceeded)
- AMBER   = REFUSAL / unverifiable / in-progress state (stopped, safe)
- RED     = DISPUTED / mismatch / fraud proven         (evidence exists)
- BLUE/CYAN = on-chain facts, transaction hashes, links to block explorer
Use color ONLY for these meanings. Nothing decorative in these hues.

Accessibility: all state colors need a text label or icon too - never color
alone. Judges may watch a compressed video where hues shift.

--------------------------------------------------------------------------------
4. PAGE COUNT AND MAP
--------------------------------------------------------------------------------

SIX pages total. Five are required, one is optional if time allows.

  P1  Landing                    (marketing, one long scroll)
  P2  Live Deal / Control Room   (THE demo stage - most important screen)
  P3  Deal Recall                (fresh-session view of one deal)
  P4  Memory Inspector           (what is in Sibyl Memory + the delete gate)
  P5  Crash Proof                (the kill-at-every-boundary results table)
  P6  Evidence & Disclosure      (OPTIONAL - signed proof + selective reveal)

Plus two non-page Figma sheets:
  S1  Component library
  S2  States & edge cases

Navigation: a single persistent top bar across P2-P6. P1 stands alone with its
own header and a "Launch demo" CTA leading to P2.

--------------------------------------------------------------------------------
P1. LANDING PAGE
--------------------------------------------------------------------------------

Purpose: explain the problem and the claim in under 30 seconds, then get the
visitor to the live demo. One long scroll. Desktop first, but must work on
mobile because it will be shared on X.

SECTION 1 - HERO
  - Headline (largest type on the site):
      "Agents that pay each other will die mid-payment."
  - Subhead:
      "AIRTIGHT makes that survivable. It writes to memory before it acts, so a
       crash can never make an agent pay twice."
  - Two buttons: [ Run the live demo ]  (primary)   [ View on GitHub ] (ghost)
  - Below the fold edge, a single strip of live-looking terminal output as
    evidence. Not a screenshot in a browser frame - a real terminal block:
        AT:IN_FLIGHT  nonce 0x87fcd790...
        -- killed --
        RESUMED  from IN_FLIGHT -> reconcile-onchain
        AT:PAID   one settlement
  - Design note: the hero must communicate "this is real software that runs",
    not "this is a concept".

SECTION 2 - THE PROBLEM (three short beats, horizontal or stacked)
  Beat 1:  "An agent pays for something."
  Beat 2:  "It dies before it knows whether the money left."
  Beat 3:  "Retry - it pays twice. Don't retry - it's stuck."
  Visual: a simple horizontal timeline with a break/glitch in the middle.
  No character illustration.

SECTION 3 - THE MECHANISM (this is the important section)
  Title: "Write before you act."
  A diagram, horizontal, five steps, showing the ORDER:
      1. agree terms      -> written to memory
      2. sign the payment -> written to memory      <- the critical one
      3. money moves
      4. payload received -> written to memory
      5. deal closed
  Show a "kill" marker that can sit between step 2 and step 3, with a caption:
      "Killed here, it wakes up holding the signed payment. It re-submits that
       exact one - same nonce - so the chain settles it once."
  Contrast callout (small, secondary):
      "Most systems write down what happened AFTER the fact. That does not help
       when the crash lands mid-payment."

SECTION 4 - THE PROOF
  A single, large, monospace evidence block. This is the money shot of the page:
      nonce stored in memory : 0x87fcd79058fbb6e7055f53b30feced9770c24496...
      nonce burned on-chain  : 0x87fcd79058fbb6e7055f53b30feced9770c24496...
      MATCH                  : YES
  With a caption: "The payment instruction we stored is the one the token
  contract consumed. Verifiable by anyone."
  Include a link out to the block explorer.
  Design the case where the two hashes are long - they must be readable, so
  consider stacking them and highlighting the matching characters.

SECTION 5 - THE TEST WE HOLD OURSELVES TO
  Full-width, high contrast, almost a warning panel:
      "Delete the memory and the product should break."
      "Ours does, on purpose. It stops paying entirely."
  With the actual output shown:
      REFUSAL: no verifiable deal state. Refusing to sign or pay.
  This section should feel heavier and more serious than the rest of the page.

SECTION 6 - WHAT IT GUARANTEES (4 items, compact grid)
  - Never pays twice          (enforced by the chain, not by trust)
  - Never pays blind          (no verifiable state, no signature)
  - Never pays off-terms      (terms committed before signing)
  - Always knows what it got  (payload recorded and checked)

SECTION 7 - BUILT ON
  Small, honest logo/word row: Sibyl Memory, Base, x402.
  One line: "Memory is Sibyl. Payments are x402 on Base. Nothing is mocked."

SECTION 8 - FOOTER
  Repo link, hackathon mention, minimal.

--------------------------------------------------------------------------------
P2. LIVE DEAL / CONTROL ROOM  *** MOST IMPORTANT SCREEN ***
--------------------------------------------------------------------------------

Purpose: perform the entire demo from the browser. The presenter clicks
buttons here on camera. Everything the terminal does must be doable here.

LAYOUT: three regions. Suggested split 30 / 40 / 30 on desktop.

REGION A (left) - THE AGENT
  A card representing the buyer agent, with:
    - Status pill:  RUNNING / KILLED / RESUMING / IDLE
    - The agent's wallet address (truncated, copyable)
    - Its balance in USDC
  Controls (real buttons, they trigger real actions):
    [ Start deal ]
    [ Kill agent ]        <- destructive styling, this is the hero interaction
    [ Restart cold ]
    A dropdown: "Kill at: [ INTENT / QUOTED / AUTHORIZED / IN_FLIGHT /
                            SETTLED / PAID / DELIVERED ]"
  DESIGN NOTE: "Kill agent" is the emotional centre of the demo. It should look
  consequential - red, slightly larger, maybe a hold-to-confirm micro
  interaction. When pressed, the whole agent card should visibly "die"
  (desaturate, a hard cut, not a gentle fade).

REGION B (centre) - THE STATE MACHINE
  A vertical or horizontal pipeline of the seven states:
      INTENT > QUOTED > AUTHORIZED > IN_FLIGHT > PAID > DELIVERED > CLOSED
  with DISPUTED as a branch off to the side (red, terminal).
  Each node shows:
    - state name
    - a checkmark when written to memory
    - the timestamp when it was written
  The CURRENT state is emphasised strongly.
  Critical detail: show clearly that memory is written BEFORE the action. Each
  node should have a small "written to Sibyl" marker that lights up first, then
  the action indicator. This is the whole product - please make it visible.
  Show the "kill window" between IN_FLIGHT and PAID as a visually distinct gap
  or danger zone - that is where the money is at risk.

REGION C (right) - LIVE LOG
  A terminal-style stream of the agent's real output lines:
      AT:INTENT demo-1
      AT:QUOTED 10000 units to 0x1957a9...
      AT:AUTHORIZED
      AT:IN_FLIGHT nonce 0x87fcd790...
      AT:SETTLED 0x195e32b1...
      AT:PAID
      AT:ATTESTED seller signed delivery - payload matches
      AT:DELIVERED
      AT:CLOSED
      DONE demo-1
  Auto-scrolling, monospace, timestamped. Lines colour-coded by the semantic
  palette. RESUMED / REFUSAL lines should be visually louder than the rest.
  Include a design for the killed state: the log stops mid-line, abruptly.

BOTTOM BAR - THE COUNTER THAT MATTERS
  Persistent, always visible, large:
      SETTLEMENTS FOR THIS DEAL:  1
  This number must never read 2. It is the single strongest visual in the whole
  product. Design it like an odometer or a counter on an instrument panel.
  Next to it: total USDC spent.

STATES TO DESIGN FOR THIS PAGE:
  - Idle (no deal yet)
  - Running (mid-deal)
  - Killed (agent dead, deal frozen mid-flight)
  - Resuming (cold restart reading memory)
  - Completed (CLOSED, green)
  - Refused (amber, agent declined to act)
  - Disputed (red, evidence held)

P3. DEAL RECALL
--------------------------------------------------------------------------------

Purpose: the "fresh session" view. A brand new process reads only what is in
memory and reports the deal. This is a required beat in the hackathon video, so
it must look authoritative and be readable on video.

This is a detail page for ONE deal. Content, in order:

  HEADER
    Deal id (e.g. demo-1), role (buyer), and a large state badge (CLOSED).

  INTEGRITY ROW - design this prominently, it is the trust signal
    terms hash      sha256 670950...21fc      [ recomputes OK ]  green tick
    disclosure root merkle 81425c...e916      7 fields committed
    The "recomputes" check means the record has not been tampered with. If it
    fails, the whole row turns red and the page shows a REFUSAL banner instead.

  PARTIES
    payer      0x2F2FfB96...b1cf
    seller     0x1957a9eF...e341
    network    base-sepolia
    price      0.01 USDC

  PAYMENT
    fingerprint  b2e126...4d41
    tx hash      0x195e32b1...  [link to block explorer]
    settled at   2026-09-05 14:43:33
    A "consumed" badge: "this fingerprint is consumed - a second payment is
    refused"

  DELIVERY
    payload sha256  8bb3fb...dced
    bytes           103
    received at     timestamp
    attestation     "seller signed delivery - payload matches" (green)
                    or "unattested" (dim) or "MISMATCH" (red)

  TIMELINE
    The full append-only transition list with timestamps:
        INTENT      2026-09-05T14:43:20.018Z
        QUOTED      ...
        AUTHORIZED  ...
        IN_FLIGHT   ...
        PAID        ...
        DELIVERED   ...
        CLOSED      ...
    Design it as a vertical timeline with the times right-aligned and
    monospaced. Show a "resumed here" marker if the deal was interrupted -
    this is important, it proves the crash happened.

  ON-CHAIN VERIFICATION PANEL - give this its own bordered panel
        tx status     SUCCESS   block 46426085
        transfer      0x2f2ffb...30b1cf -> 0x1957a9...12e341   0.01 USDC
        agreed terms  recipient OK   amount OK
        gas paid by   0xd407e4...e7f1bf  (facilitator - the buyer holds no ETH)
        nonce stored  0x87fcd790...81480
        nonce burned  0x87fcd790...81480
        MATCH         YES
    The two nonce lines should be the visual climax of the page. Consider
    aligning them so identical characters stack, and highlighting the match.

  VERDICT FOOTER
        on wake:  RESUME -> no action needed
    or  on wake:  REFUSAL -> reason
    or  on wake:  DISPUTED -> evidence available  [ view evidence ]

--------------------------------------------------------------------------------
P4. MEMORY INSPECTOR
--------------------------------------------------------------------------------

Purpose: show what actually lives in Sibyl Memory, and provide the delete
button that proves the product breaks without it. This page IS the hackathon's
pass/fail gate, so it must be unambiguous.

  HEADER
    "Sibyl Memory"  +  the store path  +  a record count.

  FOUR CATEGORY PANELS (these are the real category names, do not rename them):
    airtight-deal      the deal state machine records
    airtight-fp        consumed payment fingerprints (replay guard)
    airtight-witness   blinding nonces for selective disclosure (PRIVATE)
    airtight-att       signed delivery attestations from sellers

    Each panel shows: category name, one-line purpose, record count, and a list
    of record keys. Clicking a record opens a JSON viewer (monospace, syntax
    coloured, collapsible).

    Mark airtight-witness visibly as PRIVATE / never shared. It contains the
    secrets that make selective disclosure work.

  THE GATE - a full-width danger panel at the bottom
    Title: "Delete the memory"
    Body:  "AIRTIGHT cannot function without this. The agent will refuse to
            pay rather than risk paying twice."
    Button: [ Delete all memory ]  - destructive, requires confirmation.

    AFTER DELETION the page must transform, not just empty out:
      - All four panels show 0 records, dimmed
      - A large amber banner appears:
            REFUSAL - no verifiable deal state. Refusing to sign or pay.
      - The Control Room's "Start deal" button becomes disabled with the reason
        shown.
    Design both the before and after states. The after state is the screenshot
    that wins the gate.

--------------------------------------------------------------------------------
P5. CRASH PROOF
--------------------------------------------------------------------------------

Purpose: show the full test result - the agent killed at every point in the
deal, always settling exactly once. This is the "we tested this properly" page.

  A results table, one row per kill point, seven rows:

    KILLED AT      RESUMED FROM   SETTLEMENTS   FINAL STATE
    INTENT         INTENT         1             CLOSED
    QUOTED         QUOTED         1             CLOSED
    AUTHORIZED     AUTHORIZED     1             CLOSED
    IN_FLIGHT      IN_FLIGHT      1             CLOSED
    SETTLED        IN_FLIGHT      1             CLOSED
    PAID           PAID           1             CLOSED
    DELIVERED      DELIVERED      1             CLOSED

  The SETTLEMENTS column is the point. Every value is 1. Design so that column
  reads as a vertical column of ones - it should be impossible to miss.

  Above the table, a headline stat block:
      7 kill points     1 settlement each     0 double-payments

  Below, a short explainer for the two most important rows:
      "Killed at IN_FLIGHT: the payment had not landed. It re-submitted the
       stored authorisation and settled once."
      "Killed at SETTLED: the payment HAD landed but was not yet recorded. It
       re-submitted the same authorisation, the chain refused it, and no second
       payment occurred."

  Optional: a "Run it now" button that re-runs the suite live and fills the
  table row by row. Very strong on video if feasible.

--------------------------------------------------------------------------------
P6. EVIDENCE & DISCLOSURE  (OPTIONAL - design only if time allows)
--------------------------------------------------------------------------------

Purpose: show that AIRTIGHT produces proof a third party can check, and that
the agent can reveal selected facts without exposing everything.

  PART A - THE ATTESTATION
    A "receipt" card showing the seller's signed statement:
        signed by      0x1957a9eF...e341
        deal           <fingerprint>
        promised hash  8bb3fb...dced
        delivered hash 8bb3fb...dced
        signature      0x4e0a...
        verdict        SIGNATURE VALID / PAYLOAD MATCHES
    Design the failure variant too: delivered hash different, big red MISMATCH,
    and a note "the seller's own signature is the evidence".

  PART B - SELECTIVE DISCLOSURE
    A field-picker interface. The deal has 7 terms fields. The user ticks which
    to reveal:
        [x] price_cap_usdc      0.01
        [x] network             base-sepolia
        [ ] resource_url        (hidden)
        [ ] seller              (hidden)
        [ ] pay_to              (hidden)
        [ ] asset               (hidden)
        [ ] max_amount_required (hidden)
    Then a "shareable proof" output panel showing the generated blob, with a
    line: "verifiable against the committed root without revealing the hidden
    fields".
    Visual metaphor: a document with some lines legible and others sealed -
    but keep it literal and data-like, not skeuomorphic.

S1. COMPONENT LIBRARY (Figma sheet, not a page)
--------------------------------------------------------------------------------

Please build these as reusable components with variants:

  1.  StateBadge        variants: INTENT, QUOTED, AUTHORIZED, IN_FLIGHT, PAID,
                        DELIVERED, CLOSED, DISPUTED
  2.  VerdictBanner     variants: RESUME (green), REFUSAL (amber),
                        DISPUTED (red)
  3.  HashValue         a truncated hash with copy button and optional
                        explorer link. Variants: short, full, matched-pair
  4.  DataRow           label + monospace value + optional status icon
  5.  Panel             bordered container with title and optional action
  6.  TerminalLog       the streaming log block, with line-type variants
                        (normal, state-change, resumed, refusal, error)
  7.  Button            primary, secondary, ghost, destructive; plus disabled
                        and loading states for each
  8.  StateMachineNode  pending / current / done / skipped / danger
  9.  StatBlock         big number + label (for "1 settlement", "7 kill points")
  10. JsonViewer        collapsible monospace record display
  11. Toast/Inline      for action results

--------------------------------------------------------------------------------
S2. STATES AND EDGE CASES (Figma sheet)
--------------------------------------------------------------------------------

Please design these explicitly - they will all appear during the demo:

  - Empty:      no deals yet
  - Loading:    action in progress (a deal takes ~3-6 seconds end to end)
  - Killed:     agent dead, deal frozen, UI must look interrupted not broken
  - Resuming:   reading memory, before it knows what it will do
  - Refusal:    amber, calm, explanatory - this is CORRECT behaviour, it must
                not look like an error or a crash. Very important: a refusal is
                the product working, and the design must communicate that.
  - Disputed:   red, evidence present, action available
  - Error:      genuine failure (network down, seller unreachable) - visually
                distinct from Refusal
  - Memory deleted: the whole app degrades into the refusal state

--------------------------------------------------------------------------------
9. WHAT NOT TO DESIGN
--------------------------------------------------------------------------------

  - No login, signup, account, or settings screens
  - No pricing, plans, or billing
  - No chat interface or chatbot bubble
  - No wallet-connect flow (the agent holds its own key; the visitor does not
    connect a wallet)
  - No dashboard with fake charts. There is no chart in this product. Every
    number shown is a real, specific fact.
  - No marketing testimonials or team section
