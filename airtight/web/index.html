Write to memory before you pay.

An agent killed mid-payment cannot tell whether the money left. Retry and it pays twice; sit still and it is stuck holding nothing. AIRTIGHT writes the signed payment instruction into memory before the money moves — so a crash never leaves it guessing.

01 · The failure

The crash lands where nothing is known.

The dangerous moment is not the payment. It is the gap between submitting one and recording that it happened — where the agent has no way to tell which side of the transaction it is on.

01

An agent pays

It signs a payment instruction and sends it to be settled on-chain.

02

It dies mid-flight

OOM, deploy, dropped connection. The process stops between sending and knowing.

03

Both options are wrong

Retry and it may pay a second time. Do nothing and it may have paid for nothing.

02 · The mechanism

Write before you act, never after.

Each payment carries a nonce the token contract will honour exactly once. That nonce is what makes a payment unrepeatable — so it is written to memory before it is ever submitted. On waking, the agent re-submits what it stored rather than signing something new.

01Agree terms with the sellerwritten first
02Sign the payment authorisationwritten first
The kill window — everything past this point is unknown to the agent
03The money moveson-chain
04Payload received and hashedwritten first
05Deal closedwritten first

Killed inside that window, the agent wakes holding the signed authorisation and submits that exact one again. Same nonce, so the contract either settles it for the first time or refuses it outright. It never needs to work out which — the chain already knows.

04 · The test we hold ourselves to

Delete the memory and it stops paying

If a product still does what it claims after its memory is removed, the memory was never load-bearing. Ours is. With no verifiable record of a deal, the agent will not sign and will not pay — because starting over is how you pay twice.

$ rm memory.db
$ airtight recall demo-1

REFUSAL: no verifiable deal state for demo-1.
Refusing to sign or pay.

07 · What it guarantees

Four promises, none of which trust the seller.

Never pays twice

Enforced by the token contract, not by anyone's good behaviour.

Never pays blind

No verifiable state, no signature. Refusal is the correct outcome.

Never pays off-terms

Terms are committed before signing. A changed price is refused.

Always knows what it got

The payload is hashed and checked against what the seller signed for.
